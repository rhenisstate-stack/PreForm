## 1. Rollback Architecture & Recovery Classification

When an operational anomaly or critical regression occurs post-deployment, rollback must be swift, deterministic, and non-destructive. PrepFord classifies rollbacks across 4 operational tiers:

```
[ Incident Detection ] (Health Probe Failure / Error Rate > 1.0% / HMAC Rejection)
         │
         ├─────────────────────────────┬─────────────────────────────┐
         ▼                             ▼                             ▼
[ Tier 1: Ingress / Traffic ]   [ Tier 2: Application Code ]   [ Tier 3: Config Rollback ]
  (Shift 100% traffic to          (Revert Next.js / API          (Revert misconfigured
   prior stable deployment)        containers to prior SHA)       secrets / CORS origins)
                                       │
                                       ▼
                            [ Tier 4: Database Disaster Recovery ]
                              (Restore pre-migration pg_dump snapshot)
```

## 2. Multi-Tier Rollback Procedures

### 2.1 Tier 1: Frontend Application Rollback
- **Trigger:** Frontend runtime exceptions, asset 404s, client hydration failures.
- **Action:** Revert traffic to previous known-good deployment:
  - *Vercel:* Execute `vercel rollback` via CLI or promote previous deployment via dashboard.
  - *Container / K8s:* Revert image tag:
    ```bash
    kubectl set image deployment/prepford-web prepford-web=prepford-web:previous-sha
    ```
- **Data Loss Risk:** **Zero**.

### 2.2 Tier 2: Backend API Rollback
- **Trigger:** Kestrel crash loop, `/api/v1/health/ready` returning 503, 500 error spike.
- **Action:**
  - *Container / K8s:*
    ```bash
    kubectl set image deployment/prepford-api prepford-api=prepford-api:previous-sha
    ```
  - *Systemd / Standalone VM:*
    ```bash
    systemctl stop prepford-api
    cp /opt/prepford/releases/previous/Preform.Api.dll /opt/prepford/current/
    systemctl start prepford-api
    ```
- **Database Schema Compatibility:** Because all 9 PrepFord migrations follow a strict non-destructive **Expand-and-Contract** model, rolling back application code does not require rolling back the PostgreSQL database schema. The previous backend version continues to operate safely against the expanded schema.
- **Data Loss Risk:** **Zero**.

### 2.3 Tier 3: Configuration & Secrets Rollback
- **Trigger:** Gateway HMAC signature rejection (401), invalid `WEB_ORIGIN` (CORS errors).
- **Action:** Revert misconfigured environment variables in secrets vault / hosting environment and trigger rolling service restart.
- **Data Loss Risk:** **Zero**.

### 2.4 Tier 4: Database Disaster Recovery
- **Trigger:** Catastrophic datastore corruption or unrecoverable data loss.
- **Action:** Restore pre-migration custom-format dump (`pg_restore`):
  ```powershell
  # Clean restore into dedicated database
  pg_restore -h <db-host> -U <db-user> -d prepford_recovery --verbose --clean --if-exists --no-owner --no-privileges prepford_staging_backup_pre_deploy.dump
  ```
- **Post-Restore Verification:**
  - Verify 32 public tables present.
  - Verify 9 migration records in `__EFMigrationsHistory`.
  - Confirm examination families, revision records, and attempt snapshots match pre-deployment counts.

## 3. Recovery Objectives (RPO & RTO)

| Metric | Target Threshold | Operational Mechanism |
|---|---|---|
| **Recovery Point Objective (RPO)** | $\le 15$ minutes | Continuous WAL archiving + pre-deployment snapshots |
| **Recovery Time Objective (RTO)** | $\le 60$ minutes | Automated `pg_restore` / Blue-Green replica promotion |
| **Traffic Shift Duration** | $\le 2$ minutes | Instant edge / load-balancer routing switch |
| **Application Restart Duration** | $\le 30$ seconds | Container cold boot / Kestrel process spin-up |
