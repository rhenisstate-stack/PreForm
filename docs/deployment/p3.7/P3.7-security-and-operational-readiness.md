## 1. Authentication & Session Security Architecture

PrepFord enforces a two-tier defense-in-depth authentication model designed to separate client sessions from internal inter-service gateway requests:

1. **Client Tier (Browser ↔ Next.js BFF):**
   - Authenticated via cryptographically signed `prepford_session` cookies (HMAC-SHA256, format: `<base64urlPayload>.<base64urlSignature>`).
   - Cookie attributes: `httpOnly: true`, `secure: true` in production, `sameSite: "lax"`, path `/`.
   - Verified server-side by `verifySignedSessionToken()` in `apps/web/src/lib/session.ts`.
   - Session revocation checked against database `UserSessions` records.
2. **Gateway Tier (Next.js BFF ↔ ASP.NET Core API):**
   - Governed by `PrepfordAuthHandler` (`apps/api/Services/PrepfordAuthHandler.cs`).
   - Mutual Gateway HMAC Canonical V1 signature binding method, path (with raw query string), timestamp, nonce, body hash, and caller claims.
   - Bearer session token priority fallback with datastore token validation (`_sessionService.ValidateTokenAsync`).

### 2.1 Backend Policy Coverage (`Program.cs`)

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("RequireAdmin", policy =>
        policy.RequireRole("admin", "superadmin", "administrator"));

    options.AddPolicy("RequireSuperAdmin", policy =>
        policy.RequireRole("superadmin"));

        policy.RequireRole("exam_manager", "superadmin"));

- **Verification Evidence:**

## 4. API Security & Operational Resilience

### 4.1 Transport & Network Controls
- **HTTPS Enforcement:** `app.UseHttpsRedirection()` active in backend pipeline.
- **CORS Protection:** `AllowFrontend` CORS policy bound strictly to configured `WEB_ORIGIN`. Wildcard origins (`*`) disallowed when credentials enabled.
- **Security Headers:** Next.js and reverse proxy enforce standard security headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Strict-Transport-Security`).

### 4.2 Health Checks & Observability
ASP.NET Core implements dual-stage ASP.NET health checks:
1. **Liveness Check (`/api/v1/health/live`):** Evaluates application runtime liveness; responds with `200 OK` `Healthy` if web server process is responsive.
2. **Readiness Check (`/api/v1/health/ready`):** Executes `PostgresHealthCheck` (`apps/api/Services/PostgresHealthCheck.cs`) executing a test query against PostgreSQL. Responds with `503 Service Unavailable` if database is down or unreachable.
